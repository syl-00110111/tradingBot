# Technical Documentation of SELL Triggers

This document details the technical mechanisms governing the triggering of a **sell** order by the trading bot, based on the analysis of the source code.

## 1. Technical Process Preceding the Sale

The triggering of a sale is not just the result of a single indicator, but the outcome of a cascade of technical validations.

### Signal Detection
Everything starts in the `indicators.py` module via the `get_signals` function. Depending on the chosen **strategy** (e.g., `simple_ema`), the bot calculates technical indicators. A sell **signal** (`sell_signal`) is generated when the specific conditions of the strategy are met (e.g., moving average crossover).

### Trend Analysis
The bot evaluates the market **trend** (`Bullish`, `Bearish`, `Range`, or `Neutral`) by comparing the gap between fast and slow moving averages relative to the closing price. This trend allows for classifying the current market state.

### Profitability Verification
Before executing the order, the `TradingEngine` calls the `is_profitable` function. This function calculates whether the current price allows for a net **profit** after deducting transaction **fees**.
*   **Fees**: By default, the bot applies a rate of 0.1% per transaction (i.e., 0.2% for the **buy** / **sell** round trip).
*   **Calculation**: `min_exit_price = entry_price * (1 + fee_rate * 2)`.

### Technical Validation (Monte Carlo)
Unlike buying, **selling** does not require validation by the Monte Carlo engine. The bot prioritizes exiting the **position** as soon as the signal is confirmed and profitability is ensured, without performing an additional future probability **test** during the selling phase.

## 2. Analysis of the Restart Scenario

When a bot restart occurs while positions had been taken previously, the bot follows a rigorous state recovery procedure.

1.  **State Restoration**: At startup, the `DataManager` class (in `persistence.py`) loads the history JSON files (e.g., `trades_history_simulation.json`). It restores each open **position** with its entry price, amount, and term.
2.  **Bot State Initialization**: The `setup_bot_state` function in `bot.py` re-injects these positions into the bot's active state (`bot_state`).
3.  **Synchronization**:
    *   The `initialize_simulation` function synchronizes the inventory of the real (or simulated) wallet with the tracked positions.
    *   The `sync_live_positions` function periodically verifies that the positions tracked by the `DataManager` still exist on the exchange. If a major discrepancy is detected, the tracking is pruned to avoid errors when selling non-existent assets.

## 3. Analysis of Specific Cases

Regardless of the context (post-restart or continuous operation), the bot handles two scenarios when receiving sell signals:

### Case A: With Achievable Profit
If the current price is higher than the calculated `min_exit_price` (including fees):
*   The **sell** order is sent immediately to the exchange via `execute_sell` upon receiving the signal.
*   The position is closed and the profit is recorded in the history.

### Case B: Without Achievable Profit
If a sell signal is received but the profit is not sufficient to cover fees or reach objectives:
- The bot logs that the sell signal was ignored because profit is not yet assured.
- It continues to hold the position until a profitable exit is possible or until the user manually intervenes.

## 4. Transaction History

### What is it?
The history is the bot's persistent memory. It is a register of all completed transactions (**sell** performed) and currently open positions. It allows the bot to survive restarts without losing track of its operations.

### History Content
For each transaction, it contains:
*   The asset symbol.
*   Entry and exit prices.
*   Amounts and **fees** paid.
*   The **profit** realized (in absolute value and percentage).
*   Timestamps and data that triggered the **signal**.

### How to consult it?
The history is stored as JSON files at the root of the project:
*   `trades_history_live.json`: For transactions in live mode.
*   `trades_history_simulation.json`: For transactions in simulation mode.

These files can be opened with any text editor. Additionally, the bot displays a summary of this information on its interactive Dashboard for quick real-time consultation.
